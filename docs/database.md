# 数据库设计

## 原则

- 历史: 所有的编辑历史都应该有留痕。
- 不可变更: 可同步数据一旦插入后就不可以修改(UPDATE)，只可以进行移动(MOVE)。

## 分类

数据库大概可以分为以下几种类型
||OTID 表|SID 表|LOCAL 表|
|---|---|---|---|
|特性|有一个或多个 `OTID` 字段，用来组成主键|有一个 `SID` 字段，为记录主要内容的 digestId|只在本地工作的表|
|是否参与同步|是，需要同时考虑 `~_hist` 表的同步|是，更新时直接 ignore 即可|不参与同步，只用来记录本地 instance 的属性|
|可变性|不可变，否则同步问题无法解决|不可变，因为主键为 sid，限制了主要内容的变化|可以|

## 数据库支持

- 顶层基于 `KDb` 来实现数据库访问
- ORM: 自有实现 `chin-sql`，包括 struct 到常见 CRUD 语句的派生宏
- 目前支持如下数据库
  |数据库|依赖库|
  |---|---|
  |postgres| tokio-postgres|
  |sqlite| actor-sqlite + rusqlite|

## 关键通用字段说明

- `TID`: 负责记录每条记录的插入时间。13 位时间戳 + 3 位序列号，对于一个个人等级的知识库来说，认为一毫秒是不会产生超过 1000 条数据的，或者即使说多个节点不会在同一毫秒产生这么多数据，所以认为这个 TID 不会冲突。
- `OTID`: 负责记录每条记录所属于的元数据的产生时间。类型同上。
- `SID`: 当前记录的主要内容的 digest id。

## 同步逻辑

### 导出为文件

按照 TID 导出，逻辑相对简单。

### 网络同步

Chnots 当前的跨设备同步是 LAN 内实例到实例的点对点同步，不依赖中心服务器。整体目标偏向 AP：优先保证每个节点可以独立工作，再通过同步过程收敛到最终一致。

#### 1. 远程节点

- 本地维护一组同步 endpoint，即一系列 `ip:port`。
- 同步时逐个 endpoint 串行执行。

#### 2. 同步范围

- `LOCAL` 表不参与同步。
- `OTID` 表是主同步对象，按表独立执行增量合并。
- `SID` 表不单独做时序对比，而是由相关 `OTID` 记录在同步前后按需带出并补齐。

#### 3. 握手

握手阶段用于确认双方是否允许开始同步，并协商本轮同步窗口的起点。

- `instance_id` 相同则直接拒绝同步，避免自己和自己同步。
- `DB_VERSION` 当前要求字符串完全一致；不一致则拒绝同步。
  - 注意：当前实现不是 semver patch 兼容，而是严格相等。
- 双方分别根据 `table_name + remote_id` 查询本地保存的最近同步日志 `SyncLogTransient`。
- 如果从未同步过，则起点视为 `0`。
- 如果已经有同步日志，则先取最近一条日志；再检查这条日志之后是否存在时间窗重叠的同步记录：
  - 若存在，起点回退到这些重叠记录里最早的 `start_tid_ex`。
  - 若不存在，起点使用最近一次的 `end_sync_in`。
- 发起端拿到远端返回的 `sync_time` 后，还会结合自己本地计算出的 `sync_time`，取两者较小值作为最终起点，避免漏同步。

#### 4. 时间窗口

- 每轮同步针对单张 `OTID` 表执行。
- 起点为握手得到的 `start_ex`，终点为本轮开始时的 `TID::now()`，记为 `end_in`。
- 同步窗口语义为 `(start_ex, end_in]`。

#### 5. 建立 OTID 对照表

对每张 `OTID` 表，在本地创建一个临时对照表，字段为：

- `TID`
- `LSTATE`：本地记录状态
- `RSTATE`：远端记录状态

状态取值如下：

- `0 = Absent`
- `1 = Cur`
- `2 = Hist`

构建方式：

- 先把本地主表 `(tid, 1, 0)` 和历史表 `(tid, 2, 0)` 中位于窗口内的数据写入临时表。
- 再分页拉取远端主表和历史表的 `tid` 列表，upsert 到临时表，仅更新 `RSTATE`。
- 分页顺序为：先主表，再历史表；每页按 `tid asc` 拉取。

#### 6. 根据状态生成同步动作

遍历临时对照表中 `LSTATE != RSTATE` 的记录，生成同步动作：

|LSTATE|RSTATE|动作|
|---|---|---|
|0|1|向远端请求主表记录，拉到本地主表|
|0|2|向远端请求历史记录，拉到本地历史表|
|1|0|把本地主表记录推给远端主表|
|2|0|把本地历史记录推给远端历史表|
|1|2|本地执行 omit，将当前记录转入本地历史态|
|2|1|通知远端执行 omit，将远端当前记录转入远端历史态|

其中：

- `Push` 表示直接发送完整记录。
- `Pull` 表示先发送 `tid` 请求，再由对端回传完整记录。
- `Omit` 不表示物理删除，而是把当前版本从主表移出，保留在历史链路中。

#### 7. 记录合并规则

当前实现对 `OTID` 主表的冲突处理规则如下：

- 若目标表中不存在对应主键，则直接插入。
- 若同步的是历史表记录，则使用 `insert ignore`，已存在则忽略。
- 若同步的是主表记录且目标表中已存在同主键记录，则比较双方 `tid`：
  - 远端 `tid` 更小：远端记录作为旧版本写入历史表。
  - 远端 `tid` 更大：远端记录进入主表，原记录通过 `po_otid_commit` 的常规逻辑进入历史链路。
  - `tid` 相等：忽略。

因此，当前协议本质上是：

- 对同一主键使用 `tid` 做 last-writer-wins。
- 同时尽量保留旧版本到 `hist` 表。

#### 8. SID 表同步

- `SID` 表不参与上面的 `LSTATE/RSTATE` 比较。
- 它们由 `OTID` 同步过程中的关联 worker 负责补齐。
- 典型场景：
  - `kfile` 元信息同步前后，额外上传/下载文件内容以及内联 SID 数据。
  - `graph` 元信息同步前后，额外同步相关 `GraphData`。
- `SID` 数据提交时以插入为主，冲突时直接忽略已有记录。

#### 9. 同步日志

每张表同步完成后，双方都会各自写入一条 `SyncLogTransient`，记录：

- `remote_id`
- `table_name`
- `start_tid_ex`
- `end_sync_in`
- `sync_finish_tid`

这些日志会参与下次握手时的起点计算。

#### 10. 当前实现特征

- 同步按表串行执行，不是全局事务。
- 每张表的同步窗口固定在本轮开始时的 `end_in`，同步过程中新增的数据进入下一轮。
- 当前临时对照表在同步完成后没有显式 drop，依赖下次同步前 `drop table if exists` 覆盖重建。
