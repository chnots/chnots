# 数据库设计

## 原则

- 历史: 所有的编辑历史都应该有留痕。
- 不可变更: 可同步数据一旦插入后就不可以修改(UPDATE)，只可以进行移动(MOVE)。

## 分类

数据库大概可以分为以下几种类型
||OTID 表|SID 表|LOCAL 表|
|---|---|---|---|
|特性|有一个或多个 `OTID` 字段，用来组成主键|有一个 `SID` 字段，为记录主要内容的 digestId|只在本地工作的表|
|是否参与同步|是，需要同时考虑 `~_hist` 表的同步|是，更新时直接 ignore 即可|不参与同步，只用来记录本地 instance 的属性|
|可变性|不可变，否则同步问题无法解决|不可变，因为主键为 sid，限制了主要内容的变化|可以|

## 数据库支持

- 顶层基于 `KDb` 来实现数据库访问
- ORM: 自有实现 `chin-sql`，包括 struct 到常见 CRUD 语句的派生宏
- 目前支持如下数据库
  |数据库|依赖库|
  |---|---|
  |postgres| tokio-postgres|
  |sqlite| actor-sqlite + rusqlite|

## 关键通用字段说明

- `TID`: 负责记录每条记录的插入时间。13 位时间戳 + 3 位序列号，对于一个个人等级的知识库来说，认为一毫秒是不会产生超过 1000 条数据的，或者即使说多个节点不会在同一毫秒产生这么多数据，所以认为这个 TID 不会冲突。
- `OTID`: 负责记录每条记录所属于的元数据的产生时间。类型同上。
- `SID`: 当前记录的主要内容的 digest id。

## 同步逻辑

### 导出为文件

按照 TID 导出，逻辑相对简单。

### 网络同步

Chnots 的同步是 LAN 同步，不需要连接到中央服务器，多个实例(instance)之间进行同步，也就是说 Chnots 为 AP。我们只需要保证每个节点的可以性，然后在同步时保证最终一致性。

0. 设计远程节点
   - 维护 endpoint 列表，一系列 ip:port。
1. 握手  
   检查两个实例之间是否可以同步。
   - 数据库版本号(DB_VERSION)  
     数据库版本号应该兼容，格式 x.y.z，当 z 变化时，认为是兼容的。同时认为其他情况数据库结构已发生较大的变化，拒绝握手。
   - 最近同步版本
     通过 instance_id 判断需要开始同步的时间。
     {TODO} 详细描述怎么判断需要开始同步的时间。
2. 构建传输数据列表
   只考虑 OTID 表，SID 表由 OTID 表进行索引。
   - 建立本地的同步临时表 A， TID， LSTATE， RSTATE
   - 将本地 instance 的数据插入进去
   - 拉取远程 instance 中的数据， upsert 到 A 中，负责更新 RSTATE 字段
   - 整理数据类型
     |LSTATE|LSTATE|动作|
     |---|---|---|
     |x|x|无动作|
     |0|1|拉取到本地 main 表|
     |0|2|拉取到本地 hist 表|
     |1|0|推送到远程 main 表|
     |1|2|omit 到本地 hist 表|
     |2|0|推送到远程 hist 表|
     |2|1|通知远程进行 omit 数据|
3. 根据上面列的内容进行数据同步
